# Финансовые отчёты — архитектура

Веб-приложение для ведения ДДС / P&L / Баланса. Замена Excel-шаблона.
Разработка идёт фазами: сначала полностью рабочее локальное приложение без бэкенда,
затем хранилище, затем остальные формы отчётности.

## Принципы

1. **Весь расчёт на фронтенде.** Бэкенд — тонкое хранилище (CRUD + auth), без бизнес-логики.
   Две реализации движка формул гарантированно разъедутся.
2. **Шаблон отделён от данных.** Шаблон — структура статей и формулы. Данные — значения.
   Смена шаблона не трогает введённые операции.
3. **Единственный источник истины — журнал операций.** Отчёты не хранятся, а вычисляются.
   Ничего вычисляемого в БД не пишем.
4. **Деньги — целые минорные единицы (тийины) в BigInt.** Никаких float. Никогда.
5. **Формулы по умолчанию из шаблона, но переопределяемы пользователем** с возможностью отката.

## Ключевые решения и почему

- **Счета — записи справочника, а не колонки.** В Excel счета были столбцами, поэтому добавление
  счёта требовало переверстки листа и правки всех формул. Здесь счёт — строка в `accounts`,
  а колонки таблицы строятся динамически.
- **Периоды выводятся из дат операций,** а не задаются фиксированным набором колонок.
  Ключ периода — `YYYY-MM`, год обязателен.
- **Строки отчёта бывают трёх механик, а не одной.** Это главное отличие от классической
  финмодели: часть строк — агрегаты журнала, часть — формулы.
- **Ссылки в формулах по `code`, а не по координатам A1.** Перестановка и переименование
  статей не должны ломать формулы.

## Модель данных (концептуально)

Одна и та же структура работает и локально (JSON / IndexedDB), и в MySQL.

- `accounts` — счета: код, название, валюта, порядок, признак активности.
- `categories` — статьи затрат/доходов: код, название, направление (in / out / transfer), порядок.
- `rates` — курсы валют: валюта, дата, курс. Курс подтягивается по дате операции, не вводится в строке.
- `opening_balances` — начальные остатки: счёт, дата, сумма. **Отдельная сущность, не операция.**
- `operations` — журнал: id, дата (реальный тип date), тип, описание, категория, примечание.
- `operation_lines` — проводки: operation_id, account_id, amount, currency.
  Одна операция = N проводок. Приход/расход — одна строка, переброска — две.
- `templates` / `items` — дерево статей отчёта: код, родитель, порядок, форма (cf/pl/bs),
  вид (header / input / agg / calc), правило агрегации, формула по умолчанию.
- `item_overrides` — пользовательские формулы поверх шаблонных.
- `projects`, `scenarios` — контейнер расчёта и версии (план / факт). Заложить в модель сразу,
  даже если в Фазе 1 используется единственный дефолтный экземпляр.

Модель проводок (`operation_lines`) заменяет широкую таблицу «операция × 4 колонки счетов».
Она же делает переброску структурно корректной: две проводки с суммой ноль.

## Виды статей отчёта

- `header` — заголовок раздела, не считается.
- `input` — ручной ввод (начальные остатки, плановые значения).
- `agg` — агрегат журнала: фильтр по типу / категории / счёту + группировка по периоду.
  Задаётся декларативно, не формулой. Покрывает большинство строк ДДС.
- `calc` — формула по другим статьям.

## Язык формул

Минимальный набор, ссылки по кодам статей:

- арифметика `+ - * /`, скобки
- `SUM(children)` — сумма дочерних статей
- `PREV(code)` — значение статьи в предыдущем периоде (основа цепочки остатков)
- `FIRST(code)`, `LAST(code)` — первый и последний период диапазона
- `TOTAL(code)` — сумма по всем периодам
- `IFERROR(expr, fallback)`

Порядок вычисления: построить граф зависимостей, топологически отсортировать,
**детектировать циклы и показывать их пользователем понятной ошибкой**, а не падать.
Расчёт по всем периодам сразу, `PREV` разворачивается в порядке следования периодов.

Формула хранится в шаблоне как `formula_default`. Пользовательская правка пишется в
`item_overrides` и не затирает шаблонную. В UI у изменённой строки — маркер и действие
«вернуть как в шаблоне».

## Контрольные суммы

Выполняются после каждого пересчёта, результат виден в UI постоянно, а не по кнопке:

1. `остаток на начало + приход − расход = остаток на конец` по каждому счёту и в целом.
2. Сумма проводок переброски = 0.
3. Переброски не входят ни в приход, ни в расход.
4. Операция без проводок или с нулевой суммой — предупреждение.
5. Дата вне диапазона периодов проекта — предупреждение, строка не теряется молча.

Расхождение показывается числом и подсветкой строки. Молчаливое несхождение недопустимо:
в исходном Excel отчёт просто переставал видеть строки за пределами зашитого диапазона.

## Фазы

### Фаза 0 — каркас
Vite + React + TypeScript, состояние в памяти, данные из фикстуры (журнал из учебного файла).
Никакого хранилища. Цель — увидеть журнал на экране.

### Фаза 1 — движок и ДДС
Справочники счетов и категорий, ввод операций, движок формул, отчёт ДДС с остатками
и разбивкой по категориям, все контрольные суммы. Сохранение в IndexedDB, экспорт/импорт JSON.
**На этой фазе приложение полностью заменяет Excel-шаблон.** Всё тестируется локально.

### Фаза 2 — редактор шаблона и Excel
Редактирование дерева статей, правка формул с откатом к дефолту, версии шаблона.
Импорт и экспорт .xlsx (SheetJS). Экспорт нужен обязательно — файл всё равно попросят.

### Фаза 3 — P&L и Баланс
Добавление двух форм в то же дерево статей, связки между формами
(чистая прибыль → нераспределённая прибыль, конечный остаток ДДС → денежные средства баланса),
проверка `актив = пассив`. Здесь понадобятся исходные шаблоны P&L и Баланса.

### Фаза 4 — бэкенд
FastAPI + MySQL 8. Эндпоинты только на чтение/запись справочников, журнала, шаблонов.
Миграции Alembic. Клиент переключается с IndexedDB на API через один слой репозитория —
он должен быть абстрагирован уже в Фазе 1.

### Фаза 5 — Docker и TWA
docker compose: mysql / api / web(nginx) / caddy для TLS.
Авторизация Telegram: валидация `initData` по HMAC-SHA256 на бэкенде, обмен на собственный JWT
в заголовке `Authorization` (cookie в webview ненадёжны). Тема из `themeParams`.
Мобильный режим таблицы: один период на экран, статьи списком, свайп между периодами.
Полная сетка — только десктоп.

## Технологии

- Фронт: React + TypeScript, Zustand или Redux Toolkit, Vite.
- Таблица: AG Grid Community (MIT). Свой грид не писать: копипаст из Excel,
  закреплённые колонки и редактирование стоят месяцев.
- Формулы: собственный парсер (набор операций мал) + свой обход графа зависимостей.
  HyperFormula не брать без проверки лицензии (GPLv3 / коммерческая).
- Бэк: FastAPI, SQLAlchemy, Alembic, MySQL 8.
- Тесты: Vitest на движок формул и контрольные суммы — обязательно с Фазы 1.

## Антипаттерны

- Дублировать движок расчёта на бэкенде.
- Хранить вычисленные значения в БД.
- Использовать float или number для сумм.
- Зашивать диапазоны данных фиксированной длиной.
- Определять период парсингом строки даты без года.
- Начинать с редактора шаблонов раньше работающего отчёта.
- Хранить курс валюты в строке операции вместо справочника курсов.
- Смешивать начальный остаток с операциями журнала.

## Готовность фазы

Фаза считается завершённой, когда учебные данные за январь–март вводятся с нуля,
все контрольные суммы сходятся, а результат совпадает с исходным Excel-отчётом
по каждой строке и каждому периоду.
